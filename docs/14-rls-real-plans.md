# 14. RLS на реальных планах 1С: от простого условия до ограничения БСП

[← Соединения на реальных планах](13-joins-real-plans.md) · [Оглавление](../README.md)

Исследование ограничений доступа на уровне записей (RLS) на **фактических** планах учебных баз 1С, пойманных в Profiler по SPID сеанса пользователя ([вопрос 69а](08-1c-specifics.md#69а-практика-как-поймать-свой-запрос-1с-в-profiler-и-получить-его-план)). Две части:
- **простое ограничение** «реквизит в списке разрешённых значений» — без индекса и с индексом;
- **реальное ограничение БСП** справочника «Транспортные средства» (шаблон `#ПоЗначениямРасширенный`): что платформа отправляет в СУБД, как это выглядит в плане, почему пользователь видел то ничего, то всё, и сколько это будет стоить на 10 000 записях.

Короткая теория — в [вопросе 75](08-1c-specifics.md#75-rls-и-производительность).

## 1. Как платформа встраивает RLS в SQL

СУБД ничего не знает о ролях 1С. Платформа **дописывает условие ограничения в SQL каждого запроса** к таблице с ограничением — и к таблицам, присоединённым через точку. Если запрос читает документ, его табличную часть и три справочника с ограничениями, условий будет пять.

| Вид ограничения в 1С | Что появляется в SQL | Как выглядит в плане |
|---|---|---|
| `Организация В (&Список)` | `OR` / `IN` по параметрам | Predicate при скане или **Merge Interval + Seek** (раздел 2) |
| Несколько полей: `Организация В (…) И Склад В (…)` | Два набора `OR` через `AND` | Seek по одному полю, второе — в Predicate |
| Через точку: `Контрагент.Группа В (…)` | `LEFT JOIN` к справочнику + условие | Соединение на **каждую** проверяемую строку |
| С подзапросом к регистру прав | `EXISTS` / `IN (SELECT …)` | **Left Semi Join** с таблицей прав |
| Шаблоны БСП (`#ПоЗначениям…`) | Несколько `EXISTS` к служебным регистрам, ветки `OR`, `CASE … = CASE …` | Semi Join, Concatenation, Filter (раздел 6) |
| Производительный вариант БСП (ключи доступа) | Один `EXISTS`: «ключ доступа объекта входит в разрешённые ключи» | Semi Join с одной-двумя служебными таблицами по индексам |

**Режимы `РАЗРЕШЕННЫЕ` и «все».**
- С `ВЫБРАТЬ РАЗРЕШЕННЫЕ` недоступные строки молча отбрасываются: условие RLS работает как **фильтр**.
- Без `РАЗРЕШЕННЫЕ` (режим «все») недоступная строка среди нужных — это **ошибка доступа**: условие проверяется, а не сужает выборку.

Для списков и отчётов используют `РАЗРЕШЕННЫЕ`.

**Главное правило диагностики:** проверять производительность **под пользователем с ограничениями**. Под полными правами условий RLS в SQL нет вовсе, и план другой.

## 2. Простое ограничение: реквизит в списке разрешённых значений

Ограничение «организация документа в списке разрешённых» платформа подставила как условие по трём параметрам — по одному на разрешённое значение (`varbinary(16)` — ссылки):

```sql
… FROM dbo._Document14 T1
WHERE T1._Fld32RRef = @P1 OR T1._Fld32RRef = @P2 OR T1._Fld32RRef = @P3
```

### 2.1. Поле не индексировано

```text
Clustered Index Scan _Document14 (PK)                прочитано 80, отдано 1, 4 чтения
   Predicate: _Fld32RRef = @P3 OR _Fld32RRef = @P2 OR _Fld32RRef = @P1
```

Индекса нет, поэтому читается вся таблица, а условие RLS проверяется для **каждой** строки ([вопрос 44](05-plans-operators.md#44-seek-predicate-и-predicate-residual)). Оценка — по автостатистике `_WA_Sys_…` столбца. На таблице в миллион документов это скан всей таблицы ради нескольких строк — для **каждого** запроса **каждого** пользователя с ограничением.

### 2.2. Поле индексировано («Индексировать»)

```text
Nested Loops   Outer References: Expr1010, Expr1011, Expr1012          1 строка
├─ Merge Interval                                                      3 диапазона
│  └─ Sort
│     └─ Compute Scalar
│        └─ Concatenation
│           ├─ Compute Scalar ← Constant Scan     диапазон [@P1, @P1]
│           ├─ Compute Scalar ← Constant Scan     диапазон [@P2, @P2]
│           └─ Compute Scalar ← Constant Scan     диапазон [@P3, @P3]
└─ Index Seek _Document14_ByFieldFld32 (Реквизит + Ссылка)   3 выполнения, 6 чтений
```

«Гора операторов» — стандартный приём SQL Server для `IN (@p1, @p2, @p3)` и `OR` по одному столбцу **с параметрами** (подробно — [вопрос 44, «Merge Interval»](05-plans-operators.md#merge-interval-поиск-по-списку-параметров)):

| Оператор | Что делает |
|---|---|
| Constant Scan × 3 | Пустая строка-заготовка на каждый параметр |
| Compute Scalar × 3 | Параметр → диапазон поиска: начало `@Pi`, конец `@Pi`, флаги `62` (обе границы включены — «равно») |
| Concatenation | Три диапазона в один поток |
| Sort | Сортировка диапазонов по началу |
| **Merge Interval** | **Слияние одинаковых и пересекающихся диапазонов** |
| Nested Loops → Index Seek | По одному поиску на каждый уникальный диапазон |

**Зачем столько операторов.** Значения параметров неизвестны при компиляции, а план кэшируется для любых значений. Если среди них окажутся одинаковые (`@P1 = @P2`), отдельные поиски прочитали бы одни строки дважды и **вернули бы их дважды**. Поэтому сервер в момент выполнения сортирует диапазоны, сливает повторы и ищет по каждому уникальному диапазону один раз. С литералами (`IN (1, 2, 3)`) это не нужно: план — один Index Seek с несколькими ключами.

### 2.3. Сравнение

| | Без индекса | С индексом |
|---|---|---|
| Доступ | Clustered Index Scan + Predicate `OR` | Merge Interval + Index Seek × 3 |
| Прочитано строк | 80 (вся таблица) | 1 |
| Логических чтений | 4 | 6 |
| Optimization Level | FULL | TRIVIAL |
| `QueryHash` | `0x7AF19745DB2102E3` | `0x7AF19745DB2102E3` — **тот же** |
| `QueryPlanHash` | `0xCB7D537DA5F48F1E` | `0xC7E6A99C3D0D546D` — **другой** |

- На 80 строках индекс даже проиграл по чтениям (6 против 4). На сотнях тысяч документов — наоборот: скан всей таблицы против нескольких коротких поисков ([вопрос 42](05-plans-operators.md#42-table-scan-clustered-index-scan-index-seek-всегда-ли-scan--плохо)).
- Тот же `QueryHash`, другой `QueryPlanHash` — запрос тот же, план сменился из-за нового индекса ([вопрос 13](02-query-pipeline.md#13-кэш-планов-когда-план-берётся-из-кэша-а-когда-компилируется)).
- Число параметров равно числу разрешённых значений пользователя: у пользователей с разным числом значений разные тексты и разные планы ([вопрос 15](02-query-pipeline.md#15-ad-hoc-параметризованный-запрос-и-хранимая-процедура)).

**Вывод:** поля, по которым строится ограничение, **индексировать**.

## 3. Ограничение БСП: справочник «Транспортные средства»

Справочник `ТранспортныеСредства` (`_Reference389`), роль «ЧтениеДанныхБухгалтерии», право «Чтение» с ограничением:

```text
#Если &ОграничениеДоступаНаУровнеЗаписейУниверсально #Тогда
#ДляОбъекта("")
#Иначе
#ПоЗначениямРасширенный("Справочник.ТранспортныеСредства", "", "",
"ЛЕВОЕ СОЕДИНЕНИЕ Справочник.Организации КАК ОбособленныеПодразделения
 ПО Т.Собственник.ГоловнаяОрганизация <> ЗНАЧЕНИЕ(Справочник.Организации.ПустаяСсылка)
    И (Т.Собственник.ГоловнаяОрганизация = ОбособленныеПодразделения.ГоловнаяОрганизация
       ИЛИ Т.Собственник.ГоловнаяОрганизация = ОбособленныеПодразделения.Ссылка)
    ИЛИ Т.Собственник = ОбособленныеПодразделения.ГоловнаяОрганизация",
"", "",
"НЕ Т.Собственник ССЫЛКА Справочник.Организации", "ИЛИ",
"Организации", "Т.Собственник",                       "ИЛИ (",
"Организации", "Т.Собственник.ГоловнаяОрганизация",   "И",
"", "Т.Собственник.ГоловнаяОрганизация <> ЗНАЧЕНИЕ(Справочник.Организации.ПустаяСсылка)", ") ИЛИ",
"Организации", "ОбособленныеПодразделения.Ссылка",    "",
… )
#КонецЕсли
```

### 3.1. Две ветки: какой механизм работает

| Ветка | Когда действует | Что в запросе |
|---|---|---|
| `#ДляОбъекта("")` — **производительный (универсальный)** вариант | Включена константа «Ограничивать доступ на уровне записей универсально» | Ограничение описано в модуле менеджера (`ПриЗаполненииОграниченияДоступа`). Для каждого объекта **заранее**, в фоне, рассчитывается ключ доступа. В запросе остаётся одна проверка «ключ объекта среди разрешённых» |
| `#ПоЗначениямРасширенный(…)` — **стандартный** вариант | Иначе | Всё условие ниже **встраивается в SQL каждого запроса** и вычисляется на лету |

Всё дальнейшее — стандартный вариант (так работает учебная база).

### 3.2. Логика ограничения

Параметры шаблона после таблицы и соединения идут тройками «вид доступа, поле или выражение, оператор». Пустой вид доступа означает обычное условие без проверки прав:

```text
Запись разрешена, если:
      НЕ Т.Собственник ССЫЛКА Справочник.Организации                 — владелец не организация (или пуст)
  ИЛИ разрешена организация Т.Собственник                           — разрешён сам владелец
  ИЛИ (    разрешена организация Т.Собственник.ГоловнаяОрганизация
       И   Т.Собственник.ГоловнаяОрганизация <> ПустаяСсылка )      — разрешена его головная организация
  ИЛИ разрешена организация ОбособленныеПодразделения.Ссылка        — разрешено одно из подразделений
```

По смыслу: транспортное средство видно, если пользователю разрешена организация-владелец, её головная организация или любое подразделение той же «семьи» организаций. Записи, чей **владелец не организация**, видны **всем** — так задумано ограничением.

### 3.3. Что в нём заранее настораживает

- **Четыре `ИЛИ` на верхнем уровне** — ни один индекс не превратит проверку в поиск ([вопрос 26](03-optimizer.md#26-sargable-предикат)).
- **Точка от реквизита составного типа** (`Собственник`: организация или другое): `LEFT JOIN` с проверкой типа ссылки, причём выражение встречается трижды ([вопрос 73](08-1c-specifics.md#73-точка-от-составного-типа-и-выразить)).
- **`ИЛИ` в условии соединения** — только Nested Loops, N × M сравнений ([вопросы 47а](05-plans-operators.md#47а-признаки-неэффективного-join-в-плане-и-что-с-ними-делать), [74](08-1c-specifics.md#74-или-в-условиях-и-соединениях-замена-на-объединить-все)).
- **Три проверки «разрешена организация …»** — каждая разворачивается в подзапросы к служебным регистрам БСП.

## 4. Почему пользователь видел «всё» или «ничего»: настройка прав

В ходе исследования пользователь сначала видел **весь список**, потом, с ролью, выданной напрямую, — **ничего**, и только с ролью через профиль ограничение заработало. Типичные причины по убыванию частоты:

| № | Причина | Как проверить |
|---|---|---|
| 1 | **Другая роль даёт чтение без ограничения.** Права ролей складываются через «ИЛИ»: одна неограниченная роль открывает всё | Полный список ролей пользователя, у каждой — право «Чтение» на справочник и наличие ограничения |
| 2 | **Роль выдана напрямую, а не через профиль группы доступа.** БСП считает права **по группам доступа** | Роль должна входить в профиль группы, где состоит пользователь (раздел 6.1: роль напрямую → 0 строк) |
| 3 | **Вид доступа «Организации» в режиме «Все разрешены»** — значение по умолчанию | Группа доступа → вид доступа «Организации» → «Разрешены выбранные» и список (раздел 6.2) |
| 4 | **Выключено «Ограничивать доступ на уровне записей»** | Администрирование → Настройки пользователей и прав |
| 5 | **Вид доступа не используется** (например, учёт по одной организации) | Доступность вида доступа в группе / профиле |
| 6 | **Данные:** собственник не организация или пуст — запись видна всем по логике ограничения | Запрос ниже |
| 7 | **Изменения не применились:** нужен повторный вход; в универсальном варианте — завершение фонового обновления доступа | Перезайти; статус обновления доступа |

```bsl
ВЫБРАТЬ ТИПЗНАЧЕНИЯ(Т.Собственник) КАК ТипСобственника, КОЛИЧЕСТВО(*) КАК Количество
ИЗ Справочник.ТранспортныеСредства КАК Т
СГРУППИРОВАТЬ ПО ТИПЗНАЧЕНИЯ(Т.Собственник)
```

**Диагностика по SQL** (сравните SQL под пользователем и под администратором):

| Что видно | Вероятная причина |
|---|---|
| SQL **такой же**, как под администратором | Ограничение не применяется (п. 1, 4, 5) |
| Есть служебные таблицы БСП, проверка права группы на таблицу возвращает 0 строк | Роль не через профиль (п. 2) |
| Проверки выполняются, но всё проходит: значения не найдены, режим «Все разрешены» | Вид доступа не ограничен (п. 3) |
| Условия работают, строк всё равно много | Данные (п. 6) |

## 5. Трасса: три запроса вместо одного

Под пользователем выполнялся простой запрос:

```bsl
ВЫБРАТЬ РАЗРЕШЕННЫЕ ТранспортныеСредства.Ссылка КАК Ссылка
ИЗ Справочник.ТранспортныеСредства КАК ТранспортныеСредства
```

В Profiler появились **три** запроса.

**Запрос 1 — служебное чтение конфигурации платформой (не ваш запрос):**

```text
Clustered Index Scan [Config]   Predicate: PartNo = 0 AND FileName LIKE @P1 ('%')
   80 920 строк, 17 870 логических чтений, стоимость 13,2
```

Таблица `Config` хранит саму конфигурацию: метаданные, модули, формы. Этот запрос перечисляет её файлы — платформа загружает или проверяет метаданные, обычно в начале сеанса или после изменения конфигурации. Он **самый тяжёлый в трассе** (около 140 МБ через память), но к RLS не относится. В трассах 1С служебные запросы к `Config`, `Params`, `ConfigSave`, `DBSchema` нужно отличать от прикладных. Если такое чтение повторяется часто, а не раз на начало сеанса, это отдельный повод для расследования (например, частые динамические обновления).

**Запрос 2 — параметры сеанса для ограничений (служебный запрос БСП):**

```text
Top
└─ Nested Loops
   ├─ Index Seek [_InfoRg21143]          по @P1 — ссылке, связанной с текущим пользователем     2 строки
   └─ Index Seek [_Reference108_VT…]     табличная часть справочника групп доступа              4 строки
```

Вычисление групп доступа текущего пользователя: 6 чтений. Выполняется при первом обращении и запоминается в параметрах сеанса, поэтому при следующих запросах не повторяется.

**Запрос 3 — собственно запрос с ограничением** (разделы 6–7).

Во всех поисках встречается `_Fld1505 = @P (numeric = 0)` — общий реквизит-**разделитель** (область данных) типовой конфигурации. По ИТС такие поля стоят первыми во всех индексах ([вопрос 77](08-1c-specifics.md#77-как-индексы-объектов-1с-отображаются-в-индексы-субд)); в неразделённой базе значение 0.

### 6.1. План 3: роль выдана напрямую — 0 строк

```text
Nested Loops (Left Semi Join)  — «оставить ТС, если доступ есть»                       итог: 0 строк
├─ Clustered Index Seek [_Reference389] (ТранспортныеСредства)                         11 строк
└─ Nested Loops (Left Semi Join)  ← проверка, 11 выполнений (на каждое ТС)
   ├─ Nested Loops (Left Outer Join)  — «ОбособленныеПодразделения», Predicate с ИЛИ
   │  ├─ Nested Loops (Left Outer Join)  — разыменование Собственник → Организация
   │  │  ├─ Constant Scan  (SDBL_DUAL)
   │  │  └─ Filter: _TYPE = 0x08 И _RTRef = 0x000000DF  → Clustered Index Seek [_Reference223] T2   8 → 8
   │  └─ Clustered Index Seek [_Reference223] T3 (все организации)                    11 → 33 строки
   └─ Nested Loops (Left Semi Join)  — право группы на таблицу
      ├─ Index Seek [_Reference148X1] ('Справочник.ТранспортныеСредства') → [_Reference108] (группы)   11 → 44
      ├─ Index Seek [_InfoRg21801X1]                                                   44 → 0 строк ✗
      └─ Concatenation — четыре «ИЛИ» шаблона                                         НЕ ВЫПОЛНЯЛАСЬ
```

Ключевой оператор — Index Seek по `_InfoRg21801X1`: **44 выполнения, 0 строк**. 44 = 11 ТС × 4 группы пользователя. Ни одна группа **не даёт права на таблицу**: роль добавлена пользователю напрямую, а БСП считает права по группам доступа и их профилям. Проверка значений не запускалась (`Number of Executions = 0`), и Semi Join отбросил все записи.

### 6.2. План 4: роль через профиль, вид доступа «Все разрешены» — 11 строк

| | План 3 (роль напрямую) | План 4 (роль через профиль) |
|---|---|---|
| Результат | 0 строк | **11 строк** |
| Право группы на таблицу (`_InfoRg21801X1`) | 44 выполнения → 0 | 33 выполнения → **11** (11 ТС × 3 группы) |
| Ветки проверки значений | Не выполнялись | Выполнялись |
| `QueryHash` | `0x0493F563CC00A717` | `0x903522D121DA90D6` — **другой**: изменился текст (другой набор групп в `IN`) |

**Как выполнились четыре ветки «ИЛИ» (Concatenation):**

| Ветка | Условие | Выполнений | Прошло | Чтений |
|---|---|---|---|---|
| 1 | `НЕ Т.Собственник ССЫЛКА Справочник.Организации` | 11 | **3** | 0 |
| 2 | Разрешена организация `Т.Собственник` | **8** | **8** | 32 |
| 3 | Разрешена `Т.Собственник.ГоловнаяОрганизация` | **0** | — | 0 |
| 4 | Разрешена `ОбособленныеПодразделения.Ссылка` | **0** | — | 0 |

- **Короткое замыкание.** Concatenation стоит под Left Semi Join, а полусоединению нужна **одна** строка, чтобы признать «доступ есть». Как только ветка вернула строку, остальные для этой записи не запускаются. Ветка 1 (сравнение типа ссылки, 0 чтений) пропустила 3 записи с владельцем «не организация». Ветка 2 выполнялась только для оставшихся 8 и пропустила все. Ветки 3 и 4 не выполнялись ни разу. **Порядок проверок в ограничении влияет на производительность:** дешёвые — первыми.
- **Почему видны все 11.** В ветке 2 оба поиска — по значениям группы (`_InfoRg17123`) и по значениям по умолчанию (`_InfoRg17130`) — вернули 0 строк. Условие `CASE … = CASE …` сравнило «нет в списке» с «режим не по списку»: ложь = ложь, значит, разрешено. Вид доступа «Организации» в группе пользователя стоит в режиме **«Все разрешены»**, явный список пуст.

**Чтобы список фильтровался:** в группе доступа поставить «Разрешены выбранные» и выбрать организацию. Тогда ветка 2 пропустит только машины разрешённой организации, а для остальных начнут выполняться ветки 3 и 4.

**Ещё наблюдения по плану 4:**
- **Компиляция дороже выполнения:** `CompileTime = 34 мс`, `CompileCPU = 34 мс`, `CompileMemory ≈ 2 МБ`, план в кэше 160 КБ, **44 статистики** в `OptimizerStatsUsage`. Выполнение — 281 чтение за доли миллисекунды.
- **Оценка 3,3 строки против 11** — Semi Join с проверкой прав оценивается грубо ([вопрос 39](04-statistics.md#39--ошибка-оценки-кардинальности-как-найти-и-почему-она-главная)).
- **Соединение с подразделениями платится всегда:** 11 выполнений, 33 чтения, хотя ветка 4, которой оно нужно, не выполнялась ни разу. Соединение строится до Concatenation.

## 7. Цена ограничения: сейчас и при 10 000 записях

### 7.1. Цена проверки одной записи (план 4)

| Часть проверки | Чтений (11 ТС) | На одно ТС |
|---|---|---|
| Право группы на таблицу (`T4` + `T5` + `T6`) | 33 + 66 + 99 = 198 | **18** — для каждой записи |
| Соединение «ОбособленныеПодразделения» с `ИЛИ` (`T3`) | 33 | 3 — для каждой записи |
| Разыменование `Собственник` → Организации (`T2`) | 16 | 2 — для собственников-организаций |
| Ветка 2: значения и значения по умолчанию (`T10`, `T11`) | 16 + 16 | 4 — для собственников-организаций |
| Чтение самих ТС | 2 | — |
| **Итого** | **281** | **≈ 25** |

Без RLS тот же запрос — **2 чтения**.

### 7.2. Что будет при 10 000 транспортных средств

Экстраполяция при сохранении формы плана. На больших объёмах оптимизатор может перестроить план (например, закэшировать постоянную часть в Spool), но порядок величин останется таким.

| | 11 записей (план 4) | 10 000 записей (оценка) |
|---|---|---|
| Чтения без RLS | 2 | ≈ 100 |
| Чтения с RLS | 281 | ≈ 250 000 – 400 000 (≈ 2–3 ГБ через память) |
| Постоянная проверка «право на таблицу» | 198 | ≈ 180 000 |
| Соединение с организациями (`ИЛИ`) | 33 | 10 000 × число организаций |
| Компиляция | 34 мс CPU | Так же, для **каждого** набора групп доступа |
| Прокрутка динамического списка | Незаметно | Десятки тысяч чтений на порцию при строгих правах |

### 7.3. Конкретные минусы

1. **Стоимость пропорциональна размеру таблицы, а не результата.** Коррелированный `EXISTS` и `ИЛИ` из четырёх веток не дают «прыгнуть» к разрешённым записям: читаются и проверяются **все** 10 000, даже если пользователю видно 200.
2. **Постоянная проверка повторяется на каждую строку.** «Даёт ли группа право на таблицу» не зависит от записи, но вложена в коррелированный `EXISTS`: 18 чтений × 10 000 ≈ 180 000 — больше половины всей цены ради одного и того же ответа.
3. **Соединение с `ИЛИ` читает все организации на каждую запись:** в холдинге с 50 организациями — 500 000 сравнений. Платится всегда, даже если ветка 4 не нужна.
4. **Строгие права дороже.** Короткое замыкание помогает **разрешённым** записям. **Запрещённая** запись проходит **все** ветки, включая разыменование головной организации и подразделения. Пользователь с одной организацией из многих — самый дорогой случай.
5. **Динамические списки.** Чтобы набрать 50 **видимых** записей, нужно проверить столько, сколько попадётся: при доле видимых 2% это около 2 500 проверок (≈ 60 000 чтений) на каждую прокрутку.
6. **Ограничение размножается на чужие запросы:** отчёт по путевым листам с `ТранспортноеСредство.Наименование` и `РАЗРЕШЕННЫЕ` получает эту проверку для соединённых транспортных средств; плюс риск Time Out оптимизации на таком дереве ([вопрос 20](03-optimizer.md#20-достаточно-хороший-план-good-enough-plan-found-и-time-out)).
7. **Ошибки оценки ломают остальной план:** грубая оценка `EXISTS` переносится на дальнейшие соединения отчёта — Hash и большой грант вместо Nested Loops или тысячи лишних поисков.
8. **Компиляция и кэш планов:** 34 мс CPU на компиляцию, разные наборы групп — разные тексты и планы, перекомпиляции при обновлении статистики служебных регистров (у `_InfoRg17130` в плане `ModificationCount = 150`, [вопрос 14](02-query-pipeline.md#14-перекомпиляция-и-её-причины)).
9. **Индексы почти не помогают:** обращения к служебным регистрам уже идут Seek по индексам. Цена не в отсутствии индексов, а в **числе выполнений**.

## 8. Что делать

1. **Производительный (универсальный) вариант ограничений БСП** — главное средство. Вся логика шаблона уходит в фоновый расчёт ключей доступа. В запросе остаётся одно полусоединение «ключ объекта входит в разрешённые ключи групп пользователя»: без повторяющейся постоянной проверки, без соединений с `ИЛИ`, с возможностью Hash-полусоединения при одном чтении таблицы ключей. Переход меняет механизм прав во всей базе — по методике БСП для вашей версии.
2. **Индексировать поля ограничений** в простых ограничениях (раздел 2): скан превращается в поиск.
3. **Сужать выборку до проверки прав** в своих запросах: отбор по периоду и организации, временные таблицы. Чем меньше строк дойдёт до `EXISTS`, тем дешевле.
4. **Привилегированный режим** для серверного кода, где права проверены иначе (проведение, обмены, регламентные задания), — осознанно, с учётом требований безопасности.
5. **Не переписывать ограничения типовой конфигурации без необходимости:** изменения потеряются при обновлении, легко ошибиться в правах. Сначала измерить и рассмотреть универсальный вариант.
6. **Регламентное обновление статистики** служебных регистров БСП вместе с остальными таблицами.
7. **Измерять на реальном объёме и под пользователем:** тестовая копия, 10 000 записей, «Разрешены выбранные», план и `STATISTICS IO` под этим пользователем.

## 9. Чек-лист диагностики RLS

1. Запрос под **пользователем с ограничениями**, SQL — из технологического журнала (`DBMSSQL`, фильтр `Usr`) или Profiler по SPID.
2. Отделить служебные запросы: `Config`, параметры сеанса.
3. Сравнить SQL с тем же запросом под администратором: всё лишнее добавлено RLS.
4. В тексте: вшитые литералами группы доступа, `SDBL_DUAL`, `_RTRef` (номер таблицы в hex), `CASE … = CASE …`.
5. В плане:
   - Left Semi Join и `Number of Executions` проверки (на каждую строку?);
   - Concatenation: какие ветки выполнялись и сколько раз;
   - соединения с `ИЛИ` (Nested Loops на все строки);
   - проверка права группы на таблицу (0 строк — права не через профиль);
   - `CompileTime` и число статистик на SELECT.
6. Пересчитать чтения на одну проверяемую запись и умножить на реальный размер таблицы.
