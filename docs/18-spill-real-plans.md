# П8. Spill и memory grant на реальном плане 1С

[← Блокировки и взаимоблокировка](17-deadlock-real-trace.md) · [Оглавление](../README.md) · [Sort в запросах 1С →](19-sort-1c-experiments.md)

Короткий эксперимент на том же регистре, что в [П6](16-sniffing-real-plans.md#1-стенд). План, построенный под 513 строк, получил 449 952, и сортировка ушла в tempdb. Следующий вызов SQL Server сам выдал больше памяти (memory grant feedback). Главный вывод неожиданный: после исправления памяти запрос **не стал быстрее**. Spill был симптомом, а платили за неверный план.

Теория — [вопросы 48–49](05-plans-operators.md#48-sort-и-hash-match-aggregate-блокирующие-операторы-и-spill), сигнатура в трассе — [кейс 5](11-case-studies.md#кейс-5-select-который-пишет-spill-в-tempdb).

## 1. Запрос

```bsl
ВЫБРАТЬ ПЕРВЫЕ 100000
	Т.Ключ,
	Т.Количество,
	Т.Комментарий
ИЗ
	РегистрСведений.ТестSniffing КАК Т
ГДЕ
	Т.Склад = &Склад
УПОРЯДОЧИТЬ ПО
	Т.Количество УБЫВ
```

```sql
exec sp_executesql N'SELECT TOP 100000
T1._Fld54,
T1._Fld56,
T1._Fld57
FROM dbo._InfoRg53 T1 WITH(NOLOCK)
WHERE (T1._Fld55 = @P1)
ORDER BY (T1._Fld56) DESC',N'@P1 numeric(10)',1
```

`WITH(NOLOCK)` платформа добавляет при чтении в автоматическом режиме вне транзакции. Сортировка по ресурсу `Количество`, а индекса по нему нет, поэтому в плане обязательно будет **Sort**. Сортировке нужна память, и её размер определяется **до выполнения**, по оценке строк ([вопрос 49](05-plans-operators.md#49-memory-grant)).

Порядок вызовов:
1. `EXEC sp_recompile N'dbo._InfoRg53';`.
2. Склад 2 — 513 строк.
3. Склад 1 — 449 952 строки, **тот же план из кэша**.
4. Ещё раз склад 1.

> **Урок постановки.** В первой попытке между вызовами план компилировался заново, и каждый склад получал свой план со своей памятью. Spill не возникает, пока план с маленькой выдачей памяти не применён к большому объёму. Нужен именно сценарий sniffing из [П6](16-sniffing-real-plans.md): компиляция под маленькое значение, выполнение с большим.

## 2. Три вызова одного плана

План везде один (`QueryPlanHash 0x486470287FF21872`): Index Seek → Key Lookup → **TopN Sort**, построен под склад 2.

| | a1: склад 2 | **a2: склад 1** | **a3: склад 1 ещё раз** |
|---|---|---|---|
| Compiled / Runtime | 2 / 2 | **2 / 1** | **2 / 1** |
| Строк на входе Sort | 513 | 449 952 | 449 952 |
| `GrantedMemory`, КБ | 1 024 | **1 024** | **68 408** |
| `MaxUsedMemory`, КБ | 56 | **1 024** — всё | 40 224 |
| `IsMemoryGrantFeedbackAdjusted` | No: First Execution | No: Accurate Grant | **Yes: Adjusting** |
| `LastRequestedMemory`, КБ | 0 | 1 024 | **1 024** |
| Предупреждение на Sort | — | **SpillToTempDb, SpillLevel 2** | — |
| tempdb: запись / чтение, страниц | — | **5 594 / 5 594** | — |
| Key Lookup: выполнений | 513 | 449 952 | 449 952 |
| Elapsed / CPU, мс | 10 / 10 | **4 162 / 4 024** | **4 177 / 4 076** |
| Собственное время Sort*, мс | ~1 | ~1 120 | ~1 310 |

\* Время Sort минус время Nested Loops под ним.

### Spill (a2)

Где это видно:
- **жёлтый треугольник** на TopN Sort. В XML:
  ```xml
  <Warnings>
    <SpillToTempDb SpillLevel="2" SpilledThreadCount="1" />
    <SortSpillDetails GrantedMemoryKb="1024" UsedMemoryKb="1024"
                      WritesToTempDb="5594" ReadsFromTempDb="5594" />
  </Warnings>
  ```
- `UsedMemoryGrant = InputMemoryGrant = 1024` у Sort: память израсходована полностью;
- Estimated 513 против Actual 449 952 на всём пути к Sort — причина в оценке;
- ожидания `IO_COMPLETION` в `WaitStats` — запись в tempdb.

Что значат цифры:
- **5 594 страницы ≈ 44 МБ** ушло в tempdb. Это объём **всего входа** сортировки (449 952 строки × ~79 байт ≈ 36 МБ плюс служебные заголовки), а не только 100 000 строк результата. Исправленный вызов a3 использовал 40 МБ памяти, примерно столько же. По этим цифрам видно, что при `TOP 100000` сервер сортирует вход целиком, а не держит в памяти только лучшие N строк;
- **SpillLevel 2** — данные выгружались и перечитывались в несколько проходов: 1 МБ не хватило даже на слияние отсортированных кусков за один раз.

### Обратная связь увеличила выдачу памяти (a3)

Повторный вызов **того же** плана, без перекомпиляции, получил 68 408 КБ вместо 1 024 — в 67 раз больше. В плане: `LastRequestedMemory = 1024`, `IsMemoryGrantFeedbackAdjusted = Yes: Adjusting`. Это **memory grant feedback в построчном режиме** (row mode): SQL Server 2019, уровень совместимости 150. Сервер запомнил, что прошлый раз был spill, и поправил выдачу памяти для следующего выполнения. Spill исчез.

### Почему быстрее не стало

4 177 мс без spill против 4 162 мс со spill. Где время на самом деле:

```text
a2 (spill):     Key Lookup ≈ 2 100 мс │ Seek+NL ≈ 780 мс │ Sort ≈ 1 120 мс (со spill)
a3 (без spill): Key Lookup ≈ 1 940 мс │ Seek+NL ≈ 730 мс │ Sort ≈ 1 310 мс
```

- spill обошёлся примерно в ноль: tempdb на стенде быстрая, 44 МБ записались и прочитались почти мгновенно;
- основное время — **449 952 Key Lookup** плана, построенного под 513 строк ([П6, сценарий A](16-sniffing-real-plans.md#5-сценарий-a-план-под-маленький-склад-на-центральном-складе));
- правильный план для склада 1 (раздел 3) выполняется за **~0,5 с**.

> **Вывод.** Предупреждение о spill заметнее всего в плане, но здесь оно не причина, а **симптом** неверной оценки (513 против 449 952). Обратная связь лечит память, но не план. Лечить нужно оценку и план ([вопрос 48](05-plans-operators.md#48-sort-и-hash-match-aggregate-блокирующие-операторы-и-spill)). На рабочем сервере, где tempdb нагружена и запросы конкурируют за память, spill весил бы больше, но порядок разбора тот же.

## 3. Правильный план и обратная связь в обратную сторону

Тот же запрос, скомпилированный под склад 1 (b1), и его повтор (b2):

| | b1 | b2 |
|---|---|---|
| План | Clustered Index Scan → TopN Sort → Gather Streams, **DOP 12** | тот же |
| `RequestedMemory` / `GrantedMemory`, КБ | 83 712 | **62 112** |
| `MaxUsedMemory`, КБ | 41 464 (49,5%) | 41 448 |
| `IsMemoryGrantFeedbackAdjusted` | No: First Execution | **Yes: Adjusting** (`LastRequestedMemory = 83712`) |
| Spill | нет | нет |
| Elapsed / CPU, мс | 523 / 2 511 | 508 / 2 329 |

- **Выдача памяти рассчитана на 449 952 строки и 12 потоков.** Каждый поток сортирует свою долю, около 37 500 строк, и использует ~3,3 МБ. Gather Streams сливает отсортированные потоки с сохранением порядка, Top забирает первые 100 000.
- **Использовано меньше половины выданного** (49,5%), и при следующем выполнении сервер **уменьшил** выдачу памяти до 62 МБ. Это та же обратная связь, но в сторону экономии: лишняя память у одного запроса — это очередь `RESOURCE_SEMAPHORE` у других.
- Если планы для больших и маленьких значений постоянно чередуются, обратная связь «качается». После серии корректировок SQL Server отключает её для этого плана. В плане будет `No: Feedback disabled`.
- Параллелизм и `CPU ≫ Elapsed` — как в [П5](15-parallelism-real-plan.md).

## 4. Чек-лист: spill в плане

1. **Где:** жёлтый треугольник на Sort, Hash Match или Exchange; `SpillLevel`, `WritesToTempDb` / `ReadsFromTempDb`. В трассе — `Sort Warnings` / `Hash Warning`, Writes > 0 у SELECT ([кейс 5](11-case-studies.md#кейс-5-select-который-пишет-spill-в-tempdb)).
2. **Память на SELECT:** `GrantedMemory` против `MaxUsedMemory`. Израсходована вся — недооценка; использовано меньше половины — переоценка.
3. **Оценка против факта** на входе в оператор со spill. Разница на порядки — ищите её причину: sniffing (`Compiled ≠ Runtime`), статистика, табличная переменная, несаргабельное условие.
4. **Сколько стоит сам spill:** собственное время оператора, ожидания `IO_COMPLETION`. Часто дороже окажется то, что под ним.
5. **Обратная связь:** `IsMemoryGrantFeedbackAdjusted` и `LastRequestedMemory`. На SQL Server 2019 и уровне совместимости 150 она работает и для row mode, но только между выполнениями одного плана: первый вызов всё равно проливается в tempdb.
6. **Лечение** — оценка и план. Индекс, который отдаёт строки в нужном порядке, убирает Sort вместе с потребностью в памяти. Хинты `MIN_GRANT_PERCENT` в 1С недоступны.
