# Шпаргалка: 83 ответа одной-двумя фразами

[← П5](15-parallelism-real-plan.md) · [Оглавление](../README.md)

Для повторения перед аттестацией: по одной-две фразы на вопрос. Подробный ответ — по ссылке на раздел, реальные планы — в практикуме П1–П5 ([тематический указатель](../README.md#тематический-указатель)).

## 1. Хранение ([подробно](01-storage.md))
1. **Страница** — 8 КБ (заголовок 96 байт, строки до 8 060 байт, slot array). **Экстент** — 8 страниц = 64 КБ, смешанный или однородный.
1а. Строка > 8 060 байт → колонки переменной длины выносятся **целиком**, начиная с самой широкой: `(n)`-типы — в ROW_OVERFLOW_DATA, `(max)` и `xml` — в LOB_DATA (деревом страниц). Цена — лишние `lob logical reads`.
2. **Куча** — без порядка, адрес строки **RID** → RID Lookup. **Кластерная таблица** — листья B-дерева и есть таблица, адрес строки — **ключ кластеризации** → Key Lookup.
3. **B⁺-дерево** сбалансировано: корень и промежуточные уровни с разделителями, листья связаны списком; поиск — 3–4 чтения.
4. Ключ кластеризации есть в каждом НК-индексе (неявно, если не объявлен): page split не трогает НК-индексы, но **широкий ключ раздувает все индексы**.
5. **Ключевые столбцы** — на всех уровнях, по ним Seek и порядок. **INCLUDE** — только в листьях, чтобы покрыть SELECT без Key Lookup.
6. **Покрывающий индекс** содержит все нужные запросу столбцы — свойство пары «индекс + запрос», Key Lookup не нужен.
7. **Внутренняя фрагментация** — пустоты в страницах, **внешняя** — порядок страниц в файле ≠ логическому. Ориентир: REORGANIZE при 10–30%, REBUILD свыше 30%.
8. **Буферный пул** — кэш страниц в ОЗУ. Логическое чтение — из памяти, физическое — с диска; сравнивают по логическим.
9. ★ **Forwarded record** — выросшая строка кучи переехала, на старом месте указатель, чтений вдвое больше. Лечение — REBUILD или кластерный индекс.
10. ★ Seek только по **левому префиксу**: равенства, затем один диапазон. Первым ставят столбец, который есть в большинстве запросов.

## 2. Путь запроса ([подробно](02-query-pipeline.md))
11. Поиск в **кэше** → **parser** (синтаксис) → **algebrizer** (имена, типы) → **optimizer** → **execution**.
12. Парсер проверяет грамматику, алгебраизатор — смысл (имена, типы, `CONVERT_IMPLICIT`, группировку) и строит дерево реляционной алгебры: *что* вычислить, но не *как*.
13. План ищется **до разбора** по хешу текста пакета и атрибутам сеанса (SET-опции, база…); `query_hash` и `query_plan_hash` — только для анализа. Разный текст — разные записи в кэше, даже если план одинаковый.
14. **Перекомпиляция** — план найден, но перед выполнением инструкции признан устаревшим: изменилась схема, SET-опции, статистика, данные выше порога. Видно в XE `sql_statement_recompile`.
15. **Ad hoc** — план на точный текст, **prepared** — на текст + объявление параметров, **процедура** — на `object_id`. Значения параметров в ключ кэша не входят.
16. **SIMPLE** параметризует только безопасные запросы с тривиальным планом, **FORCED** — почти всё, но с риском sniffing.
17. `sp_executesql` — повтор плана, защита от SQL-инъекций и строгие типы; `EXEC(@sql)` со склейкой — новый план на каждое значение.

## 3. Оптимизатор ([подробно](03-optimizer.md))
18. **RBO** выбирает по фиксированным правилам и не смотрит на данные. **CBO** оценивает строки по статистике и берёт самый дешёвый вариант — поэтому зависит от качества оценок.
19. **Стоимость** — безразмерная оценка I/O + CPU до выполнения; сравнима только между планами одного запроса.
20. Полный перебор невозможен. **Good Enough Plan Found** — стоимость ниже порога фазы (штатно), **Time Out** — кончился бюджет преобразований: у дорогого запроса это повод упрощать его, у дешёвого — норма.
21. **Trivial plan** — альтернатив нет, перебор пропущен: план последовательный, без подсказок Missing Index.
22. Simplification → Trivial → **Search 0** (≥ 3 таблиц, порог ≈ 0,2) → **Search 1** (≈ 1,0, здесь параллелизм) → **Search 2**. Видно в свойствах корня и флагом 8675.
23. **Упрощение** по метаданным, без статистики: свёртка констант, противоречия, удаление лишних соединений (по доверенным FK — в 1С их нет), перенос фильтров вниз.
24. ★ **Memo** — группы логически эквивалентных выражений; правила исследования и реализации добавляют варианты, в каждой группе выбирается самый дешёвый.
25. ★ **Логический** оператор — *что* сделать (Join), **физический** — *как* (Nested Loops, Hash, Merge).
26. **SARGable** — `голый_столбец оператор значение`. Ломают: функция над столбцом, приведение столбца, `LIKE '%…'`, `OR` по разным столбцам.
27. Приводится тип с меньшим приоритетом. Если приводится **столбец** — нет Seek и хуже оценка (`PlanAffectingConvert`, `CONVERT_IMPLICIT` в Predicate).
28. Хинт — приказ: отключает варианты и не адаптируется к изменению данных. Сначала статистика, SARG, индексы и упрощение запроса.
28а. Сквозной пример: кэш (промах) → разбор → упрощение → оценка строк → Memo → стоимость вариантов (Hash ≈ 0,85, NL ≈ 148) → Good Enough в Search 1 → план в кэш. С индексом выигрывает NL.

## 4. Статистика ([подробно](04-statistics.md))
29. Статистика — заголовок + **вектор плотности** (по всем префиксам ключа) + **гистограмма** (≤ 200 шагов, только по первому столбцу). Гистограмма для второго столбца берётся из другой статистики, где он ведущий; что использовано — `OptimizerStatsUsage`.
29а. Оценка = доля по гистограмме × **текущее** число строк из метаданных. При росте таблицы оценки масштабируются, но о новых значениях гистограмма не знает.
29б. Статистика хранится **в базе на диске** и попадает в память при компиляции; `_WA_Sys_` тоже постоянна. Исключения — `#temp` и read-only базы (tempdb).
30. `DBCC SHOW_STATISTICS (N'dbo.T', N'имя')` — второй параметр обязателен. Шаг: `RANGE_HI_KEY` — граница, `EQ_ROWS` — равных ей, `RANGE_ROWS` — строго внутри, `AVG_RANGE_ROWS` — среднее на значение.
30а. Шаг — отрезок (пред. граница; своя граница]: на границе точное число, внутри — только сумма и среднее. ≤ 200 разных значений — каждое свой шаг, пики алгоритм делает границами.
31. 200 шагов — компромисс размера и скорости компиляции: внутри шага перекос теряется. Помогает фильтрованная статистика.
32. Граница → `EQ_ROWS`, внутри шага → `AVG_RANGE_ROWS`, вне гистограммы ≈ 1. Значение неизвестно (локальная переменная, UNKNOWN) → `Rows × density`.
33. Автосоздание — по столбцу условия (`_WA_Sys_`), синхронно при компиляции. Автообновление — при компиляции, когда изменений больше **500 + 20%** (2016+: MIN с **√(1000·n)**).
34. **FULLSCAN** — точно и дорого (по умолчанию при REBUILD), **SAMPLE** — быстро, но теряет пики; выборка идёт по страницам. Закрепить процент — `PERSIST_SAMPLE_PERCENT`.
35. **Восходящий ключ**: новые значения правее гистограммы, оценка ≈ 1 строка. Лечение — обновление статистики, новый CE.
36. Старый CE: s1·s2·s3 (независимость). Новый: **exponential backoff** s1·s2^½·s3^¼.
37. CE 120+ по-другому считает корреляцию, восходящие ключи и соединения; модель видна в `CardinalityEstimationModelVersion`.
38. `#temp` — статистика и точные оценки, но перекомпиляции. `@table` — без статистики, оценка 1 строка (до 2019).
39. ★ Ошибка оценки — главная причина плохих планов: от неё зависят доступ, соединение, память, параллелизм. Ищут расхождение Estimated и Actual (у NL — с учётом выполнений) и смотрят `OptimizerStatsUsage`.
39а. У результата вложенного запроса нет статистики — после `GROUP BY` / `HAVING` оценка по догадкам. Временная таблица даёт реальное число строк, статистику и отдельную оптимизацию шага; цена — tempdb и перекомпиляции.

## 5. План ([подробно](05-plans-operators.md))
40. **Estimated** — без выполнения, только оценки. **Actual** — тот же план плюс факт: строки, выполнения, время, чтения, грант, ожидания, spill.
41. Данные идут **справа налево**, управление — слева направо (`GetNext`). Операторы бывают потоковые и блокирующие.
42. Scan не всегда плох (маленькая таблица, большая доля строк, агрегат, `TOP`), Seek не всегда хорош. Сравнивают прочитанное и возвращённое, а не названия операторов.
43. **Key / RID Lookup** — дочитывание строк по одной через NL. Опасен на тысячах строк; лечится INCLUDE, меньшим числом столбцов и правильной оценкой.
44. **Seek Predicate** — навигация, лишнее не читается. **Predicate** — проверка каждой прочитанной строки; признак проблемы — Rows Read ≫ Actual Rows.
44а. «Гора операторов» перед Index Seek (динамический Seek, Merge Interval) — границы поиска вычисляются при выполнении, условие остаётся в Seek Predicates. Это безвредно; тревожно — `CONVERT_IMPLICIT` на столбце.
45. **NL** — мало строк сверху + индекс снизу, любое условие. **Merge** — оба входа отсортированы, равенство. **Hash** — большие неотсортированные входы, равенство, память.
46. Внешний (верхний) вход NL читается один раз, внутренний (нижний) — по разу на каждую строку сверху. Сверху должно быть мало строк, снизу — Seek.
47. Merge отбрасывает меньший ключ, потому что входы отсортированы; без сортировки нужен Sort. Внутренний Merge останавливается, когда кончился любой вход.
47а. Неэффективный JOIN: NL с огромным числом выполнений при недооценке, скан или Index Spool снизу, Key Lookup на каждую строку, spill у Hash, Sort перед Merge, размножение строк. Лечат оценку, индекс по полю соединения, типы и условие.
48. **Sort** и **Hash Aggregate** блокирующие и получают память по оценке. Не хватило — **spill** в tempdb (виден только в фактическом плане).
49. **Memory grant** выдаётся до старта по оценке строк: мал — spill, велик — другие ждут `RESOURCE_SEMAPHORE`.
50. **Stream Aggregate** — вход отсортирован, памяти не нужно. **Hash Aggregate** — любой вход, нужна память.
50а. Индекс, упорядоченный по ключу `ORDER BY` / `GROUP BY` (после равенств из WHERE), убирает Sort и даёт Stream Aggregate. Работает, только если индекс покрывает запрос (кроме `TOP N`).
51. **Spool** кэширует поддерево во worktable. Index Spool обычно значит «не хватает индекса», Eager Spool в UPDATE — защита от Halloween-эффекта.
52. Параллельный план — если стоимость выше **cost threshold** (5) и MAXDOP > 1; фактический DOP сервер выбирает при каждом запуске. Параллелизм не уменьшает работу: сначала сокращают чтения.
53. Предупреждения: PlanAffectingConvert, ColumnsWithNoStatistics, SpillToTempDb, ExcessiveGrant, NoJoinPredicate, UnmatchedIndexes. Устаревшая статистика предупреждения не даёт.
54. ★ Missing Index — взгляд одного запроса: не видит существующих индексов, записи и нагрузки, ключи ставит механически. В 1С — «Индексировать» или дополнительный индекс КОРП, а не ручной `CREATE INDEX`.
55. ★ Проценты стоимости — оценки до выполнения: неверная кардинальность, UDF, spill и ожидания в них не отражены.
55а. Анализ по стоимости: общая стоимость → самые дорогие операторы и ветки → из чего стоимость → **сверка с фактом** → исправление и сравнение «до/после».

## 6. Параметры и кэш ([подробно](06-params-cache.md))
56. **Sniffing**: план строится под значения параметров того вызова, который его скомпилировал, и используется для всех. Вредно при перекосе данных; локальные переменные не подсматриваются.
57. `ParameterCompiledValue` ≠ `ParameterRuntimeValue` + Estimated ≪ Actual; разброс min/max в DMV, несколько планов в Query Store.
58. RECOMPILE, OPTIMIZE FOR, UNKNOWN, **разные процедуры** (не IF в одной!), покрывающий индекс, Query Store, PSP (2022).
59. `sys.dm_exec_query_stats` + текст + план; сортировать и по сумме, и по среднему. План в кэше — предполагаемый, до перезапуска.
60. **Query Store** — история запросов, планов и метрик в самой базе; умеет закреплять план и навешивать хинты (2022).

## 7. Профайлер и метрики ([подробно](07-profiler-metrics.md))
61. Для долгих запросов — **RPC:Completed** (для 1С главное) и **SQL:BatchCompleted** со столбцами Duration, CPU, Reads, Writes и фильтрами.
62. GUI-трасса гонит события по сети и тормозит сервер, а Showplan очень дорог. Нужны серверная трасса с фильтрами или лучше XE.
63. **XE** фильтрует до сбора данных и пишет асинхронно, событий больше, `system_health` уже хранит дедлоки.
64. Duration ≈ CPU + ожидания. **Большое Duration при малом CPU — запрос ждал**: блокировку, диск, сеть, память.
65. `STATISTICS IO` — логические, физические и read-ahead чтения по таблицам; `STATISTICS TIME` — компиляция и выполнение, CPU и elapsed.
66. Ожидания: **PAGEIOLATCH** — диск, **LCK_M_*** — блокировки, **CXPACKET** — параллелизм или перекос, **SOS_SCHEDULER_YIELD** — CPU.
67. ★ Медленный запрос работает: CPU и Reads растут, `blocking_session_id = 0`. Заблокированный спит: `LCK_M_*`, `blocking_session_id ≠ 0`.

## 8. 1С ([подробно](08-1c-specifics.md))
68. Платформа подставляет RLS, раскрывает виртуальные таблицы и точку (LEFT JOIN), ВТ превращает в `#tt` и шлёт `sp_executesql`. Таблицу по имени определяет `ПолучитьСтруктуруХраненияБазыДанных()`.
69. Цепочка: замер производительности (строка кода) → ТЖ `DBMSSQL` + `plansql` (SQL, Context, dbpid) → XE / Profiler (Reads, план). dbpid = SPID.
69а. Свой запрос в Profiler: менеджер временных таблиц держит соединение → SPID из консоли кластера → фильтр по SPID → выполнить запрос в том же сеансе.
70. Условие в параметрах виртуальной таблицы попадает **в каждую часть** до группировки, в `ГДЕ` — после агрегации всех данных. Для `СрезПоследних` может отличаться и результат.
71. Условие соединения не попадает внутрь виртуальной таблицы, оценка агрегата грубая. Лечение — ВТ + отбор в параметрах.
72. `ИНДЕКСИРОВАТЬ ПО` нужен, если ВТ заметного размера и по полю потом соединяют или отбирают. Пакет уходит в СУБД по одному запросу и по одному соединению, данные ВТ остаются в tempdb.
73. Точка от составного типа — LEFT JOIN **со всеми** таблицами типа. Вместо неё `ВЫРАЗИТЬ(… КАК Тип)` + отбор `ССЫЛКА`.
74. `ИЛИ` по разным полям — скан, `ИЛИ` в соединении — только NL. Замена — `ОБЪЕДИНИТЬ ВСЕ` с защитой от дублей.
75. RLS встраивается в SQL каждого запроса: больше соединений, `ИЛИ`, грубые оценки. Проверять под пользователем; главное средство в БСП — производительный вариант на ключах доступа.
76. Итоги = остатки по месяцам до **периода рассчитанных итогов** + текущие. Держать период на конце прошлого месяца.
77. У всех таблиц 1С кластерный индекс; «Индексировать» → Реквизит + Ссылка, «с доп. упорядочиванием» → + Код / Наименование / Дата. Движения регистра кластеризованы по Период + Регистратор + НомерСтроки.
78. ★ Разные движки: в клиент-серверном варианте добавляются сеть, оценки и sniffing, блокировки и RLS; на больших объёмах СУБД выигрывает.

## 9. Практика ([подробно](09-practice.md))
79. Rows Read против Rows и саргабельность → ключ: равенства + диапазон → INCLUDE → сверка с существующими индексами → «до/после».
80. Сначала проверить оценку (не sniffing ли), затем INCLUDE и лишние столбцы; если покрыть нельзя — скан.
81. Недооценка сверху → NL на 500 000 выполнений. Причины: статистика, восходящий ключ, sniffing, `@table`, несаргабельность, корреляция.
82. Ждёт или работает → меняется ли план (Query Store, min/max) → sniffing, статистика, блокировки, ARITHABORT.
83. Замер → ТЖ (Context, dbpid) → XE (Reads, план) → разбор → исправление в 1С → замер «до/после» под пользователем.
