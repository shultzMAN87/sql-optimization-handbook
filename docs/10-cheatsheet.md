# Шпаргалка: 83 ответа одной-двумя фразами

[← Раздел 9](09-practice.md) · [Оглавление](../README.md)

Для повторения перед аттестацией. Подробности — по ссылке на раздел.

## 1. Хранение ([подробно](01-storage.md))
1. **Страница** — 8 КБ (заголовок 96 байт, строки до 8 060 байт, slot array). **Экстент** — 8 страниц = 64 КБ, смешанный или однородный.
1а. Строка > 8 060 байт → колонки переменной длины выносятся **целиком**, начиная с самой широкой: `(n)`-типы → **ROW_OVERFLOW_DATA** (указатель 24 Б), `(max)`/xml → **LOB_DATA** (корень 24–72 Б). `(max)` по умолчанию лежит в строке, пока помещается. Большое значение хранится **деревом** страниц. Цена — `lob logical reads`.
2. **Куча** — без порядка и дерева, адрес строки **RID** (файл:страница:слот) → RID Lookup. **Кластерная** — листья = таблица, адрес строки = **ключ кластеризации** → Key Lookup.
3. **B-дерево**: корень и промежуточные уровни с разделителями, листья связаны списком. Кластерный: листья = строки; некластерный: ключ + INCLUDE + указатель.
4. Ключ кластера — указатель в каждом НК-индексе: page split не трогает НК-индексы, ключ «бесплатно» покрывает запросы; зато **широкий ключ раздувает все индексы**, а его UPDATE дорог.
5. **INCLUDE** — только в листьях, без сортировки и seek. Нужен, чтобы покрыть SELECT без утолщения дерева. Ключевые столбцы — для WHERE/JOIN/ORDER BY.
6. **Покрывающий индекс** содержит все нужные запросу столбцы → нет Key Lookup. Свойство пары «индекс + запрос».
7. **Внутренняя фрагментация** — пустоты в страницах (больше страниц и чтений). **Внешняя** — порядок страниц в файле ≠ логическому (хуже read-ahead при сканах). REORGANIZE 10–30%, REBUILD > 30%.
8. **Буферный пул** — кэш 8-КБ страниц в ОЗУ. **Логическое** чтение — из памяти, **физическое** — с диска. Оптимизируют по логическим.
9. ★ **Forwarded record** — выросшая строка кучи переехала, на старом месте указатель → двойные чтения. Лечение: `ALTER TABLE … REBUILD` или кластерный индекс.
10. ★ Seek только по **левому префиксу**: равенства, затем один диапазон. Гистограмма есть только по первому столбцу. Ставить первым столбец, который есть в большинстве запросов.

## 2. Путь запроса ([подробно](02-query-pipeline.md))
11. Кэш → **parser** (синтаксис) → **algebrizer** (имена, типы) → **optimizer** → **execution**.
12. Парсер проверяет грамматику (ошибка 102), алгебраизатор — смысл (208, 207, 209, 8120): разрешает имена, выводит типы и **CONVERT_IMPLICIT**, проверяет группировку, раскрывает view и `*`. Результат — **дерево операций реляционной алгебры** (σ выборка, π проекция, ⋈ соединение, γ группировка): *что* вычислить, но не *как*.
13. **Кэш планов** — хранилища SQLCP (ad hoc/prepared), OBJCP (процедуры), PHDR (деревья view). Поиск **до парсера**: хеш сырого текста всего пакета (или object_id) + атрибуты кэш-ключа (SET-опции, dbid, user_id…). Не найдено → парсер → автопараметризация → повторный поиск → алгебраизатор и оптимизатор. `query_hash` / `query_plan_hash` — только для анализа.
14. **Перекомпиляция**: план проверяется лениво перед выполнением каждой инструкции — версия схемы объектов (Schema changed), SET-опции, `sp_recompile`, обновлённая статистика при изменённых данных (Statistics changed), изменения данных выше порога (сначала автообновление статистики), отложенная компиляция `#temp`. Видно: XE `sql_statement_recompile` (`recompile_cause`), `plan_generation_num`, счётчик SQL Re-Compilations/sec. Вытеснение из кэша — не перекомпиляция, а новая компиляция.
15. **Ad hoc** — план на точный текст (засорение кэша, sniffing нет). **Prepared** — текст + объявление параметров. **Процедура** — по object_id. У двух последних есть sniffing. План `sp_executesql` переиспользуется, если текст, **строка объявления параметров** (`int` ≠ `bigint`, `nvarchar(5)` ≠ `nvarchar(7)`) и SET-опции совпадают. **Значения** в ключ не входят: они влияют только на форму плана при компиляции.
16. **SIMPLE** параметризует только «безопасные» запросы с тривиальным планом. **FORCED** — почти всё, риск sniffing.
17. `sp_executesql`: повтор плана, **нет SQL-инъекций**, OUTPUT, строгие типы. `EXEC(@sql)` со склейкой — новый план на каждое значение и дыра в безопасности.

## 3. Оптимизатор ([подробно](03-optimizer.md))
18. **RBO** (Rule-Based) — фиксированные приоритеты способов доступа, данные не учитываются: «есть индекс — используй», даже если подходит 95% строк. **CBO** (Cost-Based) — много вариантов, оценка строк по статистике, выбор самого дешёвого. Правила в CBO порождают варианты, выбирает стоимость. Слабое место CBO — оценки.
19. **Стоимость** — безразмерная оценка I/O + CPU до выполнения. Сравнима только между планами одного запроса.
20. Полный перебор невозможен (10 таблиц — 17,6 млрд форм дерева), оптимизатор минимизирует компиляцию + выполнение. **Good Enough Plan Found** — стоимость ниже порога стадии (≈ 0,2 / 1,0), штатно. **Time Out** — кончился бюджет преобразований (не секунд, воспроизводимо), план может быть плохим: упростить запрос, разбить на ВТ. «Хороший» — это оценка, а не реальность. Бюджет съедают: много JOIN (в т.ч. скрытых — view, CTE, EXISTS/IN), UNION, агрегации, OR и длинные IN, много индексов, секции, повтор Search 1 для параллелизма. В 1С — виртуальные таблицы, точка от составного типа, RLS. Стоимость = цена выполнения; бюджет = сколько задач потратить на поиск, назначается по стоимости.
21. **Trivial plan** — альтернатив нет, перебор пропущен (`Optimization Level = TRIVIAL`). Всегда последовательный, без Missing Index.
22. Simplification → Trivial → **Search 0** (≥ 3 таблиц, < 0,2) → **Search 1** (< 1,0, параллелизм) → **Search 2** (всё, возможен таймаут). Увидеть: свойства корня (Optimization Level, CompileTime), снимок `sys.dm_exec_query_optimizer_info`, флаг 8675 (cost и tasks по фазам).
23. Упрощение по метаданным: удаление лишних JOIN, свёртка констант, противоречия → Constant Scan, перенос фильтров вниз, IN/EXISTS → semi join, OUTER → INNER. Ещё: транзитивность (`A = B AND B = 10` → `A = 10`), удаление неиспользуемых столбцов. Без статистики и стоимости. Противоречие с CHECK — только при доверенном ограничении и литерале. Деревья до/после — флаги 3604 + 8606.
24. ★ **Memo** — группы эквивалентных выражений, входы — группы. Правила исследования и реализации, стоимость у физических элементов, победитель в каждой группе. Правила трансформации: шаблон → замена; исследования (JoinCommute, GbAggBeforeJoin) и реализации (JNtoNL/HS/SM, GbAggToStrm/HS); ~400 правил, Promise. Сработавшие — снимок `sys.dm_exec_query_transformation_stats`; отключить — `QUERYRULEOFF` / `DBCC RULEOFF` (ошибка 8622, если плана не построить).
25. ★ **Логический** — *что* (Join), **физический** — *как* (NL / Hash / Merge).
26. **SARGable**: `голый_столбец оператор значение`. Ломают: функция над столбцом, приведение **столбца**, `LIKE '%…'`, OR по разным столбцам. Отрицания (`<>`, `NOT IN`) формально SARGable (раскладываются на диапазоны), но обычно выбирают почти всю таблицу → скан. Редкие «все, кроме X» — фильтрованный индекс (с параметром не сработает без RECOMPILE).
27. Приводится тип с меньшим приоритетом. Если приводится **столбец** — нет seek и хуже оценка. Видно по **PlanAffectingConvert** и `CONVERT_IMPLICIT` в Predicate.
28. Хинт — приказ, отключает варианты и не адаптируется к изменениям данных. Сначала статистика, SARG, индексы, упрощение.
28а. Сквозной путь: кэш (промах) → разбор и привязка (типы, литерал приводится) → упрощение (фильтры к таблицам) → статистика (200 / 73 200 / ≈ 1 464 строки) → не тривиальный → Memo (JoinCommute, JNtoHS/NL/SM, GbAggToStrm/HS) → стоимость вариантов (Hash ≈ 0,85, NL ≈ 148, Merge ≈ 2–3) → Search 1, ниже 1,0 → Good Enough → план в кэш → выполнение. С индексом по CustomerId выигрывает NL ≈ 0,7.

## 4. Статистика ([подробно](04-statistics.md))
29. Статистика — «справка» о распределении значений, по ней оптимизатор оценивает число строк (а от оценки — Seek/Scan, соединения, грант, параллелизм). **Заголовок** (Updated, Rows / Rows Sampled, Steps) + **вектор плотности** (1/уникальных, по префиксам; Rows × density, перекоса не видит) + **гистограмма** (≤ 200 шагов, первый столбец). Значение известно → гистограмма, неизвестно (переменная, UNKNOWN) → плотность.
30. `RANGE_HI_KEY` — граница; `EQ_ROWS` — равных границе; `RANGE_ROWS` — строго внутри; `DISTINCT_RANGE_ROWS` — разных внутри; `AVG_RANGE_ROWS` — среднее на значение.
31. 200 шагов — компромисс скорости и размера. На больших таблицах внутри шага только среднее, перекос теряется. Помогает фильтрованная статистика.
32. Совпало с границей → **EQ_ROWS**; внутри шага → **AVG_RANGE_ROWS**; неизвестно → **Rows × density**.
33. Автосоздание — по столбцу предиката (`_WA_Sys_`). Автообновление при компиляции: **500 + 20%** (старое) / **MIN(500 + 20%·n, √(1000·n))** (2016+).
34. **FULLSCAN** точный и дорогой (по умолчанию при REBUILD). **SAMPLE** быстрый, теряет пики (по умолчанию при автообновлении).
35. **Восходящий ключ**: новые значения правее гистограммы → оценка ~1 строка. Лечение: статистика, новый CE.
36. Старый CE: s1·s2·s3 (независимость). Новый: **exponential backoff** s1·s2^½·s3^¼.
37. CE 70 и CE 120+: корреляция, восходящие ключи, соединения. Видно в `CardinalityEstimationModelVersion`.
38. `#temp` — статистика, точные оценки, перекомпиляции. `@table` — без статистики, оценка 1 строка (до 2019), без перекомпиляций.
39. ★ Estimated ≪ или ≫ Actual (у NL сравнивать с учётом числа выполнений). Всё в плане построено на оценке, ошибка растёт вверх по дереву.

## 5. План ([подробно](05-plans-operators.md))
40. **Estimated** — без выполнения. **Actual** — плюс факт: строки, выполнения, время, чтения, грант, ожидания, spill, runtime-параметры.
41. Данные — **справа налево**, управление — слева направо (GetNext). Потоковые и блокирующие операторы.
42. Scan не всегда плох (маленькая таблица, большая доля строк, агрегат, TOP). Плохо, когда прочитано ≫ нужного. Seek тоже бывает плохим. Точка перелома.
42+. **Clustered Index Scan** читает всю таблицу (все столбцы, объём = страницы таблицы); **Nonclustered Index Seek** — спуск по дереву и отрезок листьев, но только ключ/INCLUDE/ключ кластера, остальное — Key Lookup. Сравнивают прочитанное и возвращённое, а не названия операторов.
43. **Key/RID Lookup** — дочитывание строк по одной (NL). Опасен на тысячах строк. Лечение: INCLUDE, меньше столбцов, правильная оценка.
44. **Seek Predicate** — навигация, лишнее не читается. **Predicate** — проверка каждой прочитанной строки.
45. **NL**: малый верх + индекс, любое условие. **Merge**: оба входа отсортированы, равенство. **Hash**: большие неотсортированные, равенство, память.
46. Внешний (верхний) вход читается 1 раз, внутренний (нижний) — N раз. Сверху должно быть мало строк, снизу — seek.
47. Merge отбрасывает меньший ключ, потому что входы отсортированы. Без сортировки — Sort (блокирует, память) или другой алгоритм.
47а. Неэффективный JOIN: NL с огромным Executions снизу и Estimated ≪ Actual сверху (оценка), скан/Index Spool на нижнем входе (нет индекса), Key Lookup × N (покрытие), Hash spill, Sort перед Merge, размножение строк (неполное условие), CONVERT_IMPLICIT и OR в ON. Лечение: оценка, индекс по столбцу соединения, типы, саргабельное ON, фильтровать раньше, ВТ; хинты — крайняя мера.
48. **Sort / Hash Aggregate** блокирующие: не отдают строк до конца входа. **Spill** — нехватка гранта, данные ушли в tempdb (жёлтый треугольник, только actual).
49. **Memory grant** — память под Sort/Hash по оценке, выдаётся до старта. Мал → spill, велик → `RESOURCE_SEMAPHORE` у других.
50. **Stream Aggregate** — отсортированный вход, без памяти. **Hash Aggregate** — любой вход, память.
50а. **ORDER BY** без индекса — Sort / Top N Sort (блокирующий, грант, spill). С индексом, упорядоченным по нужному ключу после равенств WHERE (с учётом ASC/DESC), — Ordered Scan/Seek без Sort. **GROUP BY**: Stream Aggregate (нужен порядок: из индекса бесплатно или через Sort) или Hash Aggregate (память). Порядок столбцов в GROUP BY не важен, `MIN/MAX` — Top (1) по индексу. Индекс должен покрывать запрос, иначе выигрывает скан + Sort/Hash (кроме `TOP N`).
51. **Spool** — кэш поддерева во worktable. **Index Spool** — «не хватает индекса». Eager Spool при UPDATE — Halloween protection.
52. Параллельный план, если стоимость > **cost threshold** (5) и MAXDOP > 1. Обмены: **Distribute / Repartition / Gather Streams**. MAXDOP — потоков на ветку.
53. PlanAffectingConvert, ColumnsWithNoStatistics, SpillToTempDb, MemoryGrant (Excessive), NoJoinPredicate, UnmatchedIndexes, Missing Index.
54. ★ Missing Index не видит существующих индексов, записи и нагрузки, механически ставит ключи, раздувает INCLUDE, лечит симптом.
55. ★ Проценты — **оценки до выполнения**: неверная кардинальность, UDF, spill и ожидания в них не отражены.
55а. Анализ по стоимости: общая стоимость (Subtree Cost на SELECT) → операторы с наибольшим Operator Cost и ветки с наибольшим Subtree Cost → из чего стоимость (I/O, CPU, строки, выполнения) → **сверка с фактом** (Actual Rows/Executions, чтения, время) → исправление и сравнение «до/после». Стоимость — оценка, не факт.

## 6. Параметры и кэш ([подробно](06-params-cache.md))
56. **Sniffing**: план компилируется под первые значения и используется для всех. Полезно при равномерных данных, вредно при перекосе.
57. `ParameterCompiledValue` ≠ `ParameterRuntimeValue` + Estimated ≪ Actual. Разброс min/max в DMV, Query Store: несколько планов.
58. RECOMPILE (точно, но CPU), OPTIMIZE FOR (стабильно под значение), UNKNOWN / локальная переменная (по плотности), **разные процедуры** (не IF в одной!), покрывающий индекс, Query Store, PSP (2022).
59. `sys.dm_exec_query_stats` + `sql_text` (вырезать инструкцию по offset) + `query_plan`. Сортировать по сумме и по среднему.
60. **Query Store** — история запросов, планов и метрик в самой базе. `sp_query_store_force_plan`, хинты (2022), FORCE_LAST_GOOD_PLAN.

## 7. Профайлер и метрики ([подробно](07-profiler-metrics.md))
61. **RPC:Completed** (для 1С — главное) + **SQL:BatchCompleted**. TextData, Duration, CPU, Reads, Writes + контекст. Фильтр по Duration/Reads/базе. Showplan — кратко.
62. GUI гонит события по сети и тормозит сервер, фильтрует поздно, Showplan дорогой. Нужны серверная трасса с фильтрами и короткое окно, а лучше XE.
63. **XE**: фильтр до сбора данных, асинхронность, > 1000 событий, гибкие приёмники, system_health с дедлоками.
64. Duration ≈ CPU + ожидания. **Большое Duration при малом CPU — запрос ждал** (блокировка, диск, сеть, память).
65. **IO**: logical/physical/read-ahead reads, scan count, worktable. **TIME**: compile и execution, CPU и elapsed.
66. `sys.dm_os_wait_stats`: **PAGEIOLATCH** — диск; **LCK_M_*** — блокировки; **CXPACKET** — параллелизм или перекос; **SOS_SCHEDULER_YIELD** — CPU.
67. ★ Медленный: CPU и Reads растут, `blocking_session_id = 0`. Заблокированный: `LCK_M_*`, `blocking_session_id ≠ 0`, CPU стоит.

## 8. 1С ([подробно](08-1c-specifics.md))
68. Платформа: RLS, виртуальные таблицы → подзапросы, точка → LEFT JOIN, ВТ → `#tt`, `sp_executesql`. `_Reference`, `_Document`, `_AccumRg`/`_AccumRgT`, `_InfoRg`, `_VT`. Точно — `ПолучитьСтруктуруХраненияБазыДанных()`.
69. Замер производительности (строка кода) → ТЖ `DBMSSQL` + `plansql` (SQL, Context, dbpid) → XE/Profiler (Reads, план). dbpid = SPID.
69а. Свой запрос 1С в Profiler: МенеджерВременныхТаблиц с ВТ держит соединение → SPID из консоли кластера («Соединение с СУБД») → фильтры DatabaseName + SPID → RPC:Completed, SQL:BatchCompleted, Showplan XML (Statistics Profile) → выполнить запрос в том же сеансе. Showplan — только с фильтром. Альтернатива — XE по session_id, ТЖ (dbpid).
70. Условие в скобках попадает **в каждую часть** UNION ALL до группировки. В ГДЕ — после агрегации всех данных. Для СрезПоследних может отличаться результат.
71. Условие соединения не попадает внутрь, оценка агрегата грубая → NL на тысячи итераций, Time Out. Лечение: ВТ + отбор в параметрах.
72. `ИНДЕКСИРОВАТЬ ПО` — если ВТ заметного размера и по полю потом соединяют или отбирают. На десятках строк не нужно.
73. Составной тип → JOIN **со всеми** таблицами типа + CASE. `ВЫРАЗИТЬ(… КАК Тип)` + **`ССЫЛКА`** (ВЫРАЗИТЬ не фильтрует).
74. ИЛИ по разным полям → скан. ИЛИ в соединении → только NL, N × M сравнений. `ОБЪЕДИНИТЬ ВСЕ` + защита от дублей.
75. RLS встраивается в SQL: больше соединений, ИЛИ, грубые оценки. Проверять под пользователем, индексировать поля ограничений, привилегированный режим, ключи доступа БСП.
76. Итоги = остатки по месяцам до **периода рассчитанных итогов** + текущие (5999-11-01). Старый период — медленное чтение, далёкий будущий — тяжёлое проведение. Держать на конце прошлого месяца.
77. «Индексировать» → индекс `(_Fld, _IDRRef)`. «С доп. упорядочиванием» → `(_Fld, код/наименование или дата, _IDRRef)` для динамических списков.
78. ★ Разные движки: запросы в цикле и сеть, оценки и sniffing, блокировки, RLS против простого локального движка. На больших объёмах СУБД выигрывает.

## 9. Практика ([подробно](09-practice.md))
79. Проверить Rows Read vs Rows и саргабельность → ключ: равенства + диапазон → INCLUDE для SELECT → сверить с существующими → проверить «до/после».
80. Сначала оценка (не sniffing ли?), затем INCLUDE, убрать лишние столбцы, иначе скан.
81. Недооценка → NL на 500 000 выполнений. Причины: статистика или восходящий ключ, sniffing, `@table`, несаргабельность, корреляция, подзапрос.
82. Ждёт или работает → план меняется? (Query Store, min/max) → sniffing / статистика / блокировки / ARITHABORT.
83. Замер → ТЖ (Context, dbpid) → XE (Reads, план) → разбор (оценки, сканы, итоги, составные типы, OR, RLS) → исправление в 1С → замер «до/после».
