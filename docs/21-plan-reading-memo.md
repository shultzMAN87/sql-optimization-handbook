# Памятка: разбор плана запроса по шагам

[← Шпаргалка](10-cheatsheet.md) · [Оглавление](../README.md)

Рабочий инструмент для разбора: откройте actual-план и пройдите **[маршрут](#маршрут)** сверху вниз. Нашли тревожный признак — переходите в таблицу **[симптом → причина](#симптом--причина)**: там варианты причин, как их проверить и что можно сделать в 1С. Перед выводом сверьтесь с **[ложными тревогами](#ложные-тревоги)**. Разделы «Справка» нужны, если надо вспомнить, что означает свойство или оператор, а теория — в вопросах, на которые ведут ссылки.

Признак в плане — повод проверить, а не доказательство. Вывод делается по совокупности признаков и подтверждается измерением ([как проверить изменение](#как-получить-план-и-проверить-изменение)).

## Симптом → причина

| Симптом | Возможные причины | Что проверить | Что можно сделать в 1С |
|---|---|---|---|
| **Результат — десятки тысяч строк, таблицы читаются без отбора** | запрос 1С выбирает больше, чем нужно: нет условия, отбор делается потом в коде | строк на выходе SELECT; нет Predicate/Seek у операторов чтения; `ASYNC_NETWORK_IO` в WaitStats | перенести отбор в запрос (`ГДЕ`, параметры виртуальной таблицы); выбирать только нужные поля; не обрабатывать большой результат в цикле. План здесь вторичен |
| **Прочитано много, отдано мало** (Scan или Seek) | нет подходящего индекса; условие не по левому префиксу ключа; условие не SARGable | Seek Predicates против Predicate; Object (какой индекс); `CONVERT_IMPLICIT` и функции над колонкой | «Индексировать» на поле; порядок измерений регистра; отбор в параметрах виртуальной таблицы; убрать `ПОДСТРОКА`/`ВЫРАЗИТЬ` из условия |
| **Оценка строк далека от факта** | устаревшая статистика; план под другой параметр; несколько связанных условий; ВТ без статистики | на каком операторе ошибка **появилась** (самый правый); OptimizerStatsUsage; Parameter List | обновить статистику (регламентное задание); разбить запрос на ВТ; упростить условия |
| **Много выполнений внутренней ветки Nested Loops** | на внешнем входе ожидали мало строк, пришло много; нет индекса для другого вида соединения | оценка и факт на верхнем (внешнем) входе; Number of Executions внизу | исправить оценку (см. выше); вынести подзапрос в индексированную ВТ |
| **Key Lookup с большим числом выполнений** | индекс находит строки, но не содержит выбираемых полей | Output List у Key Lookup — чего не хватило; Predicate у Key Lookup | выбирать только нужные поля; сначала отобрать Ссылки в ВТ, потом соединить; «Индексировать с доп. упорядочиванием», если выбираются именно эти поля |
| **Spill в tempdb** (предупреждение на Sort / Hash) | вход недооценён, памяти выдали мало; широкие строки | оценка строк на входе Sort/Hash; Estimated Row Size; SpillLevel и объём в предупреждении | исправить оценку; убрать лишние поля (особенно длинные строки); уменьшить объём до сортировки и группировки |
| **`CONVERT_IMPLICIT` над колонкой** | тип параметра не совпадает с типом колонки; составной тип | с какой стороны преобразование: над параметром — не страшно, над колонкой — ломает Seek | задать тип параметра; `ВЫРАЗИТЬ` над параметром, а не над полем; избегать неограниченных строк в условиях |
| **Elapsed ≫ CPU** | ожидания: диск, блокировки, память, клиент | WaitStats у SELECT; Physical Reads и Read Aheads; GrantWaitTime | `LCK_M_*` — искать блокирующую транзакцию (ТЖ 1С); `ASYNC_NETWORK_IO` — запрос возвращает лишние строки или код 1С обрабатывает результат по строке |
| **CPU большое, чтений немного** | тяжёлые вычисления, Sort/Hash на больших объёмах, скалярные выражения на каждую строку | Compute Scalar, Defined Values; время по операторам | упростить `ВЫБОР`, выражения, поля через точку (неявные соединения) |
| **В STATISTICS IO большие Worktable** | Spool, Sort, Hash пишут промежуточные данные в tempdb | какой оператор породил (Table/Index Spool — часто замена недостающего индекса) | дать индекс, который оптимизатор строит сам (индексированная ВТ) |
| **ВТ с оценкой в 1 строку при факте в тысячи** | статистика по `#tt` не построена или переиспользован старый план | Estimated против Actual на чтении `#tt`; сколько строк реально помещено (запрос `INSERT INTO #tt`) | `ИНДЕКСИРОВАТЬ ПО` по полям соединения; уменьшить объём ВТ |
| **Один запрос то быстрый, то медленный** | parameter sniffing: план построен под другое значение | Compiled против Runtime Value; разные QueryPlanHash в истории (Query Store) | разделить запросы под разные случаи; ВТ вместо списка значений в `В (&Список)` |
| **Параллельный план** (Gather Streams, CPU > Elapsed) | стоимость выше cost threshold for parallelism и MAXDOP сервера ≠ 1 | Degree of Parallelism у SELECT; время по потокам (F4 → ⊞); настройки max degree of parallelism и cost threshold сервера | сверить настройки сервера с рекомендациями 1С для MS SQL; сам план не «лечить», а уменьшать объём данных запроса |

Хинты SQL Server (`OPTION (RECOMPILE)`, `OPTIMIZE FOR`) в языке запросов 1С недоступны. Лечение в 1С — текст запроса, ВТ, индексы из конфигуратора, обслуживание статистики. Подробнее о неэффективных соединениях — [вопрос 47а](05-plans-operators.md#47а-признаки-неэффективного-join-в-плане-и-что-с-ними-делать), о методе расследования — [практикум П1](11-case-studies.md#метод-расследования-пять-шагов).

## Ложные тревоги

Эти признаки выглядят как проблема, но сами по себе ею не являются.

| Признак | Почему это не проблема | Когда всё же смотреть |
|---|---|---|
| **Большой `CXPACKET`** | ожидания суммируются по всем потокам; координатор ждёт весь запрос, потребители ждут производителей. Это фон любого параллельного плана | один поток работает заметно дольше остальных (по времени в разбивке по потокам) |
| **Потоки прочитали разное число строк** | скан раздаёт страницы потокам по мере готовности; после Repartition Streams потоки выравниваются | перекос виден по **времени** и после перераспределения |
| **Оценка скана с `PROBE(Bitmap)` выше факта** | фильтрация bitmap в оценке строк не учитывается; bitmap отсекает лишнее до Hash Join — это польза ([bitmap](05-plans-operators.md#bitmap-фильтр-перед-hash-match)) | оценка ошибается и на выходе самого Hash Join |
| **Scan читает больше, чем отдаёт** | если дальше уходит заметная доля таблицы (десятки процентов), скан дешевле тысяч Seek | отдаётся малая доля большой таблицы |
| **Number of Executions = числу потоков** | в параллельном плане каждый поток выполняет оператор один раз | выполнений в разы больше числа потоков |
| **Granted в разы больше Max Used на первом запуске** | `IsMemoryGrantFeedbackAdjusted = No: First Execution` — SQL Server 2019 скорректирует grant на следующих запусках ([П8](18-spill-real-plans.md)) | перерасход сохраняется при повторах и есть `RESOURCE_SEMAPHORE` |
| **Большая стоимость, большие проценты** | это расчёт, а не замер ([55](05-plans-operators.md#55--почему-процент-стоимости-оператора-может-вводить-в-заблуждение)) | фактические чтения и время подтверждают |
| **Scan + Hash Match без отбора** | для запроса «вернуть всё» это оптимальный план; улучшать нужно запрос, а не план | в запросе есть селективный отбор, а его нет в Seek Predicates |

## Справка: как читать план

**Направление.** Данные текут справа налево: от операторов чтения (Scan, Seek) к SELECT. У соединения **верхний вход — внешний**, нижний — внутренний. В Nested Loops нижняя ветка выполняется столько раз, сколько строк пришло сверху ([41](05-plans-operators.md#41-направление-чтения-плана-и-движение-данных), [46](05-plans-operators.md#46-внешний-и-внутренний-вход-nested-loops)).

**Что нарисовано на схеме:**

- толщина стрелки — число строк (в actual-плане — фактическое);
- процент под оператором — **всегда от расчётной стоимости**, даже в actual-плане; оператор с 0% может занимать почти всё время;
- подпись `105 of 34 (308%)` — факт и оценка строк, рядом время оператора;
- жёлтый треугольник — предупреждение; две стрелки в жёлтом круге — параллелизм.

**Estimated и Actual** ([40](05-plans-operators.md#40-предполагаемый-и-фактический-план)). Estimated — расчёт оптимизатора до выполнения, по нему выбирался план. Actual — счётчики, собранные во время выполнения. Смысл actual-плана — в их сравнении.

- Стоимость (I/O, CPU, Operator, Subtree) бывает только estimated. «Actual CPU Cost» не существует; фактическое CPU — в Actual Time Statistics, в миллисекундах.
- Чтения страниц и время бывают только actual.
- Оценка строк часто дана **на одно выполнение** (Per Execution), а факт — **за все** (for All Executions). Перед сравнением разделите факт на Number of Executions.

**Подсказка и F4.** Подсказка (навести мышь) — краткая выжимка: строки, выполнения, стоимость, предикаты, Object, Output List. Панель **F4** — все свойства; только там есть:

| У оператора | У SELECT |
|---|---|
| Actual I/O Statistics — logical, physical, read-ahead, LOB-чтения | QueryTimeStats — CPU и Elapsed всего запроса |
| Actual Time Statistics — Elapsed и CPU оператора, мс | WaitStats — ожидания запроса (SQL Server 2016 SP1+) |
| раскрытие ⊞ — значения по потокам (перекос при параллелизме) | MemoryGrantInfo — память |
| Defined Values — вычисляемые выражения | Parameter List — Compiled и Runtime Value |
| Scan Direction, Lookup, TableCardinality | OptimizerStatsUsage — использованная статистика |
| | Warnings, Missing Indexes, QueryHash / QueryPlanHash, Reason For Early Termination |

**Row и Batch.** Actual Execution Mode = Batch — пакетная обработка. Бывает с columnstore, а в SQL Server 2019+ (редакция Enterprise, уровень совместимости 150) и на обычных таблицах. В Row время оператора включает дочерние операторы, в Batch — только своё.

## Справка: соединения и дорогие операторы

| Оператор | Хорош, когда | Ломается, когда |
|---|---|---|
| **Nested Loops** | на внешнем входе мало строк, внизу быстрый Seek | сверху пришло намного больше строк, чем ожидалось; внизу Scan |
| **Merge Join** | оба входа уже отсортированы по ключу соединения (читаются по индексу) | перед ним появляется дорогой Sort; many-to-many (рабочая таблица в tempdb) |
| **Hash Match** | большие неотсортированные наборы, нет подходящего индекса | недооценён верхний (build) вход → мало памяти → spill |
| **Key Lookup** | найдено немного строк | тысячи выполнений: каждое — отдельный поход в кластерный индекс |
| **Sort** | небольшой объём | недооценён вход → spill; широкие строки → большой memory grant |
| **Table / Index Spool** | переиспользование промежуточного результата | Index Spool на большом объёме — оптимизатор строит недостающий индекс на каждом выполнении |
| **Scan** | нужна большая часть таблицы | большая таблица, маленький выход |

Scan сам по себе не плох, а Seek не хорош. Если нужна большая часть таблицы, скан дешевле Seek + Key Lookup на каждую строку. Подробно — вопросы [42](05-plans-operators.md#42-table-scan-clustered-index-scan-index-seek-всегда-ли-scan--плохо), [45](05-plans-operators.md#45-nested-loops-merge-join-и-hash-match), [48](05-plans-operators.md#48-sort-и-hash-match-aggregate-блокирующие-операторы-и-spill), [51](05-plans-operators.md#51-spool-table-spool-index-spool), реальные планы — [П3](13-joins-real-plans.md).

## Справка: Seek Predicates и Predicate

**Seek Predicates** решает, какие строки прочитать: спуск по индексу к нужному диапазону, остальное не читается. **Predicate** проверяет уже прочитанные строки: чтений он не уменьшает. Predicate бывает и у Scan, и у Seek.

Условие попадает в Seek Predicates, если:

- колонка — ключ индекса;
- используется левый префикс ключа: для индекса (A, B, C) подходят A, A+B, A+B+C, но не одна B;
- после неравенства (`>`, `<`, `МЕЖДУ`) следующие колонки поиск уже не сужают;
- над колонкой нет функций и преобразований типа (`CONVERT_IMPLICIT` над колонкой), нет `ПОДОБНО "%..."`.

Значок «Index Seek» не гарантирует малое чтение: диапазон может охватывать почти всю таблицу. Сравнивайте Rows Read и Rows. Подробно — [вопрос 44](05-plans-operators.md#44-seek-predicate-и-predicate-residual), динамический Seek — [44а](05-plans-operators.md#44а-merge-interval-и-динамический-seek-гора-операторов-перед-index-seek).

## Справка: чтения, время, стоимость

**Чтения** считаются в страницах по 8 КБ. Страница сначала попадает в память (буферный пул), оттуда её читает оператор ([вопрос 8](01-storage.md#8-буферный-пул-логические-и-физические-чтения)).

| Счётчик | Что это | Для чего |
|---|---|---|
| Logical Reads | обращения к страницам в памяти, повторные тоже считаются | **главная метрика объёма работы**; стабильна от запуска к запуску, по ней сравнивают варианты |
| Physical Reads, Read-Ahead | чтение с диска, когда страницы нет в памяти (read-ahead — заранее, крупными блоками) | объясняют медленный конкретный запуск; зависят от содержимого кеша |
| LOB Reads | то же для больших значений (хранилище значения, строки неограниченной длины) | запрос читает тяжёлые поля |

Оценка объёма: 100 000 logical reads ≈ 800 МБ обращений к страницам. Это не объём уникальных данных и не чтение с диска: одна страница может считаться много раз.

**Время.** CPU Time — работа процессора, Elapsed Time — общее время, точность 1 мс.

- Elapsed ≫ CPU — запрос ждал; чего именно — в WaitStats. План показывает ожидания одного выполнения; системные проблемы смотрят в `sys.dm_exec_session_wait_stats`, `sys.dm_os_waiting_tasks`, Extended Events ([вопрос 66](07-profiler-metrics.md#66-ожидания-wait-stats)).
- CPU > Elapsed — работало несколько потоков ([К8](11-case-studies.md#кейс-8-cpu-больше-duration-тяжёлый-параллельный-отчёт)).

**Стоимость** — расчёт оптимизатора в условных единицах ([вопрос 19](03-optimizer.md#19-что-такое-стоимость-плана), [55а](05-plans-operators.md#55а-анализ-плана-выполнения-по-стоимости-операторов)). Она объясняет, почему выбран план, и помогает найти кандидата, но вывод делается по фактическим чтениям и времени.

- Тяжёлый оператор ищут по собственной стоимости (%), а не по Subtree: Subtree всегда растёт к корню.
- При большой ошибке оценки строк стоимость и проценты неверны.
- Subtree у SELECT сравнивается с cost threshold for parallelism (по умолчанию 5). Это порог расчётной стоимости последовательного плана, а не времени: выше него параллельный план рассматривается, но не обязательно выбирается.
- Нельзя: переводить в секунды, сравнивать между серверами и данными, считать дешёвый план заведомо быстрым.

## Нюансы 1С

**Временные таблицы (`ПОМЕСТИТЬ`)** — самый частый источник проблем ([вопросы 38](04-statistics.md#38-временные-таблицы-и-табличные-переменные), [72](08-1c-specifics.md#72-индексирование-временных-таблиц)).

- В SQL это `#tt`. Для пакета запросов смотрите и запрос, который ВТ **наполняет** (`INSERT INTO #tt...`), и тот, который из неё **читает**.
- Главный признак беды — оценка 1 строка на чтении `#tt`, а факт в тысячи: дальше Nested Loops с тысячами выполнений.
- ВТ, которая соединяется с другими таблицами, индексируйте по полям соединения (`ИНДЕКСИРОВАТЬ ПО`).

**Виртуальные таблицы регистров** ([вопросы 70](08-1c-specifics.md#70-параметры-виртуальных-таблиц--в-скобках-а-не-в-где), [76](08-1c-specifics.md#76-таблицы-итогов-регистров-накопления-и-период-рассчитанных-итогов), [К11](11-case-studies.md#кейс-11-1с-виртуальная-таблица-остатки-с-отбором-в-где)).

- Условие в параметрах и в `ГДЕ` даёт разный SQL. Для измерений план и результат часто совпадают (проверяется по QueryPlanHash), для ресурсов и реквизитов — нет: это уже другие данные.
- `Остатки` и `Обороты` читают таблицу итогов (`_AccumRgT...`), `СрезПоследних` — таблицу срезов, если она включена. В плане будут они, а не только основная таблица регистра.
- Порядок полей в индексах регистра задаётся порядком измерений. Отбор по измерению без предыдущих уйдёт в Predicate.

**Индексы** ([вопрос 77](08-1c-specifics.md#77-как-индексы-объектов-1с-отображаются-в-индексы-субд)).

- Создаются из конфигуратора. «Индексировать» даёт (Поле, Ссылка); «Индексировать с доп. упорядочиванием» добавляет поле упорядочивания (например, Наименование или Код справочника). Точный состав проверяйте в `ПолучитьСтруктуруХраненияБазыДанных()`.
- `INCLUDE`-колонок в 1С нет, покрывающий индекс сделать нельзя. Борьба с Key Lookup — меньше полей в выборке или отбор Ссылок в ВТ.
- Ручные `CREATE INDEX` по подсказке Missing Index пропадут при реструктуризации. Каждый индекс замедляет запись и увеличивает базу.
- Реструктуризация пересоздаёт таблицу: пропадает автостатистика `_WA_Sys_...`, меняется число страниц.

**Имена и типы** ([вопросы 68](08-1c-specifics.md#68-как-запрос-1с-транслируется-в-sql-как-понять-объект-по-имени-таблицы), [73](08-1c-specifics.md#73-точка-от-составного-типа-и-выразить), [75](08-1c-specifics.md#75-rls-и-производительность)).

- Таблицы и поля (`_Reference123`, `_InfoRg456`, `_Fld789`) сопоставляются с метаданными через `ПолучитьСтруктуруХраненияБазыДанных()`. `_IDRRef` — Ссылка, `...RRef` — ссылки.
- Составной тип — несколько колонок (`_TYPE`, `_S`, `_RTRef`, `_RRRef` и др.), все участвуют в сравнениях.
- Параметры и литералы — `@P1`, `@P2`: строки `nvarchar(4000)`, ссылки и перечисления `varbinary(16)`.
- RLS и разделение данных добавляют в SQL то, чего нет в тексте запроса 1С. Анализируйте SQL из плана.

**Параллелизм.** Классическая рекомендация 1С для MS SQL — `max degree of parallelism = 1`: сервер 1С выполняет много коротких запросов одновременно, и параллелизм одного запроса отнимает ядра у остальных. Если в плане запроса 1С есть Gather Streams, проверьте, осознанно ли включён параллелизм на сервере. Сначала уменьшают чтения, потом трогают настройки ([вопрос 52](05-plans-operators.md#52-параллелизм), [П5](15-parallelism-real-plan.md#8-как-исправить)).

## Как получить план и проверить изменение

| Источник | Как | Зачем |
|---|---|---|
| SSMS, actual | `Ctrl+M`, затем выполнить; `Ctrl+L` — только estimated | основной способ для разбора |
| `SET STATISTICS IO, TIME ON` | перед запросом, итог на вкладке Messages | чтения по таблицам и время |
| Live Query Statistics | кнопка в SSMS перед запуском | долгий запрос: видно, на каком операторе он сейчас |
| Query Store | отчёты SSMS (Top Resource Consuming, Regressed Queries) | история планов: почему вчера было быстро, а сегодня медленно ([60](06-params-cache.md#60-query-store)) |
| Технологический журнал 1С | событие `DBMSSQL` со свойством `planSQLText` | план с рабочей базы, связь с кодом 1С (контекст) ([69](08-1c-specifics.md#69-как-получить-sql-текст-и-план-запроса-1с)) |
| SQL Server Profiler | *Showplan XML Statistics Profile* | разово; на рабочем сервере даёт нагрузку, лучше Extended Events ([61](07-profiler-metrics.md#61-sql-server-profiler-для-чего-он-и-что-выбрать-для-поиска-долгих-запросов), [63](07-profiler-metrics.md#63-extended-events-и-чем-они-лучше-profiler)) |
| Plan Explorer (бесплатный) | открыть `.sqlplan` | сам считает собственное время операторов и сводит чтения в таблицу |

**Проверка изменения:**

1. Зафиксировать исходное: план (`.sqlplan`), logical reads, CPU и Elapsed, число строк результата.
2. Сформулировать гипотезу: «читаем всю таблицу, потому что условие не по первой колонке индекса».
3. Изменить одну вещь.
4. Несколько запусков с теми же параметрами, на тех же данных и в том же состоянии таблиц (после реструктуризации снять и «до» заново).
5. Сравнить QueryPlanHash, logical reads и время — а не стоимость. Проверить, что результат запроса не изменился.

«Холодный» запуск на тестовой базе: `CHECKPOINT; DBCC DROPCLEANBUFFERS;`. На рабочем сервере так делать нельзя: кеш сбрасывается для всех.
